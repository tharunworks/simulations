Concepts explained

What is a WebSocket Gateway?

What: A process holding WebSocket sessions. Why: It separates long-lived connections from the Chat Service's business logic. How: It maps authenticated device sessions to sockets and writes events to those sockets. It never automatically knows sockets on other processes.

What is a subscription?

What: An application-level instruction to deliver selected events. Why: A socket alone does not establish permission to see all chats. How: Authenticate the session; validate a user against chat membership on SUBSCRIBE and upon relevant permission changes. Subscriptions are not part of WebSocket's wire protocol.

Why not publish straight to Redis?

Redis Pub/Sub is at-most-once delivery; a disconnected subscriber misses published messages. Persist the chat message in a database, then use Pub/Sub as a delivery signal. Reconnecting clients fetch missing messages by a cursor or sequence, with idempotency protection.

REST sending vs WebSocket sending

With REST, Alice uses POST /chats/42/messages and receives a 201/202 depending on the contract; Bob still receives WebSocket events. With WebSocket, Alice sends a MESSAGE_SEND frame and gets an application ACK. Same authorization, durability and deduplication requirements apply. Toggle the send mode above.

Why do we need a registry?

When Bob is connected to G2 and Alice's event is processed on G1, G1 needs to know G2 owns Bob's socket. A registry might store bob-device1 → G2 with a lease/TTL and epoch. A stale record requires retry and resync; it is not a guarantee of delivery.

What happens on server restart?

TCP/WebSocket sessions disappear, so clients reconnect and reauthenticate. Session/subscription state is rebuilt, and missed chat messages are fetched from durable storage. A Redis Pub/Sub notification sent during the restart will not be replayed automatically.

Delivery acknowledgments

Stored (server DB ACK), delivered (recipient device ACK), and read (user action) are different states. Seeing a successful call to WebSocket send does not prove that Bob's application processed the message. Device identifiers and message IDs support multi-device delivery and deduplication.

Is one WebSocket per chat needed?

No. Usually one connection per online device carries messages for multiple chats and even multiple domains. Chat ownership checks apply to each logical operation. Connections can migrate between servers only through disconnect and reconnection, not by transferring a Java WebSocketSession object.

What about Kafka instead of Redis?

Kafka provides retained records and consumer offsets, useful for downstream fan-out and replay. Redis Pub/Sub is transient. Kafka is not a substitute for a client connection registry, recipient authorization, or correct chat persistence and sequencing. A durable outbox avoids a database-write / publish dual-write gap.

Prediction practice

If Bob is connected to G2, can G1 directly call Bob's WebSocketSession?

No. Session objects belong to the process holding the socket. G1 must route a delivery command to G2; only G2 writes to Bob's connection.

If the message was stored but Redis Pub/Sub was down, was the message lost?

The durable message was not lost. The immediate delivery signal may be lost. Bob needs replay/resync after reconnect or a reliable outbox-driven delivery pipeline.

If Alice retries after an ACK was lost, should the DB store a second message?

No. Deduplicate by an authenticated sender + clientMessageId key (or equivalent unique idempotency key) and return the previously created message ID.

Interview framework · WHAT → WHY → HOW → TRADE-OFF

WHAT: Start with one Spring Boot service exposing REST and WebSocket endpoints. Later separate a WebSocket Gateway from Chat business logic.

WHY: Persistent WebSocket connections consume process resources; Chat Service work scales with message writes and membership checks. These workloads scale differently.

HOW: Authenticate sockets, authorize chat subscriptions, persist messages, acknowledge server acceptance, publish an internal delivery signal and route it to the gateway that owns Bob's connection. Resync after gaps and recheck authorization after membership changes.

TRADE-OFF: A single process avoids routing infrastructure. Broadcast Pub/Sub adds cross-node delivery but pays O(G) fan-out; targeted routing reduces fan-out but requires a registry and resilience to stale presence.

Track concurrent connections, per-gateway heap/FD usage, WS send-queue depth, p95/p99 delivery latency, DB write latency, Pub/Sub delivery fan-out, reconnect storm rate, and replay gap duration. Reconsider the design based on measured saturation rather than a fixed user count.
