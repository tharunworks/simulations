01 / Multiplex

One Redis connection, many channels

Gateway A can subscribe to all game channels needed by its connected users over one Pub/Sub connection—not one connection per user.

SUBSCRIBE game:500 game:600 game:700

02 / Fan out locally

Redis knows gateways, not browser users

Redis delivers one event to each subscribed gateway. Each gateway uses its own channel → WebSocket sessions mapping to notify the relevant local users.

1 publication→2 gateways→3 users

03 / Trade-off

Fewer Redis connections ≠ fewer deliveries

Sending to 100,000 users still requires 100,000 final messages. Redis Pub/Sub also has no replay; reconnecting clients must recover missed state from an authoritative store.

04 / Architecture notes · Patterns vs platforms

Redis Pub/Sub vs Kafka: what should we call each?

Separate the communication pattern from the system implementing it. Both Redis Pub/Sub and Kafka let publishers communicate with subscribers; Kafka also stores a partitioned event history for later consumption.

↑ Architecture diagram

Pattern / How components communicate

Publish–Subscribe (Pub/Sub)

Producers publish to a named channel or topic. Consumers express interest without the producer addressing each consumer directly. It says who gets events, not whether events are saved.

Examples: Redis Pub/Sub; Kafka topics + consumer groups

Component / Live notification delivery

Pub/Sub message broker

Routes notifications to currently subscribed clients. In Redis Pub/Sub, events are not retained for an offline subscriber to catch up. Think live radio broadcast.

Implementation: Redis Pub/Sub

Platform / Retained event processing

Distributed event streaming platform

Stores event streams in partitioned logs, lets consumers track their own progress, and supports catch-up or replay within retention. Think recorded broadcast with a playback position.

Implementation: Apache Kafka

These are not opposing categories: Pub/Sub is a messaging pattern; an event streaming platform is a class of infrastructure. Kafka implements Pub/Sub through topics and consumer groups, while also providing retention, offsets, and replay. A distributed append-only log is the underlying Kafka storage model, not a replacement term for Pub/Sub.

What changes between Redis Pub/Sub and Kafka?

Compare semantics, not brand names
DimensionRedis Pub/Sub · Ephemeral brokerKafka · Distributed event streaming
Core actionPUBLISH channel message; broker pushes to active subscriptionsProducer appends a record to a topic partition; consumers fetch records
Storage and retentionNo retained Pub/Sub message historyRetained partitioned log, bounded by retention/compaction policy
Subscriber offlineMessages published while offline are lost to that subscriberCan resume reading still-retained records using offsets
Progress and replayNo per-subscriber offset, acknowledgment, or replayPer-partition offsets; rewind and replay retained records
Multiple consumersAll subscribed connections receive a matching publicationEach consumer group independently reads; a partition is assigned to one member within a group
Ordering scopeMessages sent on a given Redis subscriber connection follow the server's delivery order; no replayable logRecords are ordered within each partition, not necessarily across a topic
Delivery / failure modelAt-most-once: no broker retry after missed deliveryProcessing/retries depend on offset commits, acknowledgments, configuration, and application idempotency
FitWebSocket update notifications, cache invalidation hints, presence signalsOrder-event pipelines, billing, analytics, audit feeds, independently replayable workflows

Concrete test: what if the consumer disconnects?

Redis Pub/Sub · Missed

10:00 Subscriber offline
10:01 PUBLISH M1
10:02 Subscriber reconnects
Result: M1 is unavailable

Redis has no Pub/Sub history to fetch. The application needs a database or another recovery source.

Kafka · Catch up

10:00 Consumer offline
10:01 Append M1 (offset 42)
10:02 Consumer resumes
Result: read offset 42

Assumes M1 is still retained and the consumer resumes from a position that includes it.

Which one for the chess/WebSocket example?

Redis
Use Redis Pub/Sub to notify gateways that a game move occurred, when the accepted move is already stored in a database. On reconnect, fetch missing moves by game sequence number.
Kafka
Use Kafka when the same event must feed billing, analytics, fraud detection, or processors that need independent catch-up and replay.
Watch
One Kafka consumer group distributes topic partitions among group members. It does not broadcast every event to every WebSocket gateway. Design routing/fan-out explicitly.
Deeper notes: Kafka consumer groups vs Redis fan-out

Redis: Gateway A and Gateway B both subscribe to game:500 → both receive each matching publication. Redis does not balance one message between these subscribers.

Kafka, one group: Gateway A and Gateway B join group ws-gateways; if game-events has one partition, only one of those gateways owns and reads that partition at a time. That is useful for dividing processing work, but not enough when both gateways have users watching the game.

Kafka, different groups: Independent services (e.g., billing, analytics) each read the retained log through separate consumer groups. Within a group, partitions divide work. Across groups, each group can see the same records.

Deeper notes: guarantees, alternatives, and how to decide

Kafka is not automatically “exactly-once business processing.” Durability and processing semantics depend on producer acknowledgments, replication, transaction settings, consumer offset commits, and how the application handles duplicate side effects.

Redis Streams is a third option: append entries with XADD; use XREADGROUP and XACK for consumer-group processing. It offers retention and pending-entry tracking, unlike Redis Pub/Sub.

Compare measured p99 end-to-end notification latency, messages/sec, bytes/sec × fan-out, consumer lag, retention period, recovery time, message-loss tolerance, and operations cost. Choose Redis Pub/Sub for disposable notifications; choose a retained event log when catch-up, replay, or independent processing is a requirement.

Interview pitch: “I'd use a Pub/Sub broker for live fan-out because the database is the source of truth and reconnects can reconcile state. I'd use a distributed event streaming platform when consumers need durable event history, offsets, replay, and independent processing. The tradeoff is the complexity and cost of managing retained streams.”
