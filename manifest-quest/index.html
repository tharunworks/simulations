Manifest Quest.

You are the player. Deliver 24 seconds of video.

Manifest is the general term for streaming metadata: a map that tells the player what media is available and where to fetch it. The media bytes arrive separately in segments.
This simulation uses HLS: its Master Playlist lists video versions and links to their Media Playlists; each Media Playlist lists segment URLs, playback durations, and order. These playlists are HLS manifests.

What is stored where?
Postgres: video ID, owner/access metadata, processing status, master object key.
S3: master.m3u8, each version’s playlist.m3u8, and video segment files.
CDN: cached copies of those S3 objects.
Client: parsed playlists and buffered media.
1 Mbps describes video bitrate; it does not mean the manifest is 1 MB. Authorization here is simulated: private playback must authorize playlists and segments too, for example with a CDN signed cookie. A signed master URL alone does not automatically authorize its children.

File guide
What does each file do?


In this game, follow three requests: master.m3u8 → 1m/playlist.m3u8 → segment-000.ts. The first two return text; the third represents media bytes.


1 · Master Playlist (an HLS manifest) — choose a version

#EXTM3U
#EXT-X-STREAM-INF:BANDWIDTH=1000000
1m/playlist.m3u8


EXTM3U identifies an HLS playlist. EXT-X-STREAM-INF describes a variant; BANDWIDTH is its peak bandwidth in bits/second. The following URI points to its media playlist. A master lists alternatives, not their segments.


Our game offers 0.5, 1, and 2 Mbps. Choosing 1 Mbps opens 1m/playlist.m3u8; it does not download the movie yet.


2 · Media Playlist (an HLS manifest) — find the next segment

#EXTM3U
#EXT-X-VERSION:3
#EXT-X-TARGETDURATION:4
#EXT-X-MEDIA-SEQUENCE:0
#EXTINF:4.000,
segment-000.ts
#EXTINF:4.000,
segment-001.ts
#EXT-X-ENDLIST


VERSION specifies protocol compatibility. TARGETDURATION bounds segment durations rounded to the nearest integer. MEDIA-SEQUENCE numbers the first segment; it does not prescribe filenames. Each EXTINF gives the following segment’s duration in seconds. ENDLIST means no further segments will be added.


This example covers 8 seconds. The game’s playlist has six entries covering 24 seconds. The second request is necessary because the master only points to this list.


3 · Segment — the media to play

A .ts segment holds encoded media in an MPEG-2 transport stream. Other HLS presentations use fragmented MP4, with initialization information referenced by EXT-X-MAP.


In our model, 1m/segment-000.ts covers video seconds 0–4 and contains 4 Mb. 1m/segment-001.ts covers seconds 4–8. Switching to 500k/segment-001.ts keeps that same time interval with fewer bits. This game displays simulated responses; it does not fetch actual video files.


How paths, storage, and caching connect

Relative paths resolve against the containing playlist’s URL.


Master:   https://cdn.example.com/video123/master.m3u8
Entry:    1m/playlist.m3u8
Resolves: https://cdn.example.com/video123/1m/playlist.m3u8

Playlist: https://cdn.example.com/video123/1m/playlist.m3u8
Entry:    segment-000.ts
Resolves: https://cdn.example.com/video123/1m/segment-000.ts


In the request mission, S3 holds all three object types. Postgres holds the video metadata and master object key. The CDN caches fetched objects; a cache hit avoids an S3 read. None of the media requests queries Postgres in this design.


For live playback, media playlists can change as segments arrive. A single-version stream can start directly from a media playlist. Cached completed playlists can be reused.


The bitrate game reopens a playlist on every selection for teaching; this does not mean a real player must download an unchanged playlist before every segment. Authorization must cover child playlists and segments too.


Protocol notes: RFC 8216, sections 3–4. Filenames here are examples; playlist contents determine their role.
Startup math: why wait 2.67 seconds for 4 seconds of video?

Two clocks are involved: download time measures how long you wait; video duration measures how long the downloaded content plays.


  1. Read the playlist: #EXTINF:4.000 says the segment contains 4 seconds of video.
    2. 

  2. Calculate its size: at 1 Mbps, each second of video needs 1 megabit. So 1 Mbps × 4 seconds = 4 Mb (0.5 MB).
    3. 

  3. Calculate the wait: a network delivering 1.5 megabits per second downloads those bits in 4 Mb ÷ 1.5 Mbps = 2.67 seconds.
    4. 

  4. Start playback: this game waits for the first complete segment. Nothing played during that wait, so all 4 seconds remain buffered.


At startup: buffer = 0 seconds remaining + 4 seconds downloaded = 4 seconds. We do not subtract the startup wait, because playback has not begun.

After startup: playback consumes the buffer while the next segment downloads. Another 1 Mbps segment on the same network takes 2.67 seconds: buffer after arrival = max(0, 4 − 2.67) + 4 = 5.33 seconds (rounded). The player watched 2.67 seconds while downloading another 4 seconds of video.


Units: Mb = megabits; MB = megabytes; 8 Mb = 1 MB. Mbps = megabits per second. The 2.67 seconds above are elapsed download time, not content seconds.


Reading the inventory: checked boxes mark downloaded segments, including ones already played. The buffer bar measures downloaded content still waiting to play. The played counter measures content already watched.


This model assumes constant segment bitrate and network throughput during each request, complete-segment buffering, and no request or decoding overhead. Real startup can also include manifest requests, initialization data, and player buffering thresholds.


How this model works · assumptions & sources
This is a simulation, not a video player. Each segment holds 4 seconds. Its size is bitrate × 4 megabits. Download time is size ÷ network throughput. Playback starts after the first download; during later downloads the buffer drains by one second per elapsed second. Segments become playable only when fully downloaded. Startup wait is measured separately from stalls. No request latency, audio, decoding, variable sizes, or parallel requests are modeled.
The network is revealed before each turn to teach the arithmetic. Real players estimate future throughput and can be surprised. All versions cover the same timeline; switching versions never restarts the movie. The demo uses a constant-rate approximation; HLS BANDWIDTH declares peak bandwidth. The manifests and media files can live in object storage; Postgres can store the master object key.
Protocol reference: HLS · RFC 8216. Confidence: high for the stated simplified model.
