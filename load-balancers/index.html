1. Architecture comparison

Green = client-to-server direction; blue = server-to-client direction. Diagrams are logical packet/connection paths, not physical cabling.

TypeDiagramTCP & packet behaviorState & tradeoffs
L4 NAT
Network address translation

Request through LB · Response through LB

1 end-to-end TCP connection. Backend completes the TCP handshake with the client.

LB rewrites destination IP/port on requests and reverses the translation on responses.

Keeps flow/NAT mappings and a local backend table.

LB processes both directions: bandwidth, PPS, and concurrent flow capacity matter.
L4 DSR
Direct Server Return

Request through LB · Direct return

1 end-to-end TCP connection. LB forwards inbound packets, often by changing the Ethernet destination MAC.

Server accepts traffic for the VIP and sends responses directly.

LB can maintain per-flow backend affinity.

Less return-path bandwidth at LB; requires VIP and routing/ARP configuration on backends.
L4 Full Proxy
TCP-level proxy

Forward payload bytes · Return payload bytes

2 independent TCP connections: client↔LB and LB↔server.

Proxy terminates TCP but need not parse HTTP. Example: HAProxy mode tcp.

Maintains TCP socket and buffering state on both sides.

Allows transport-level control, with added memory and processing overhead.
L7 Proxy
HTTP reverse proxy

*Backend TCP connections may be pooled, reused, or multiplexed.

Separate client- and server-side connections in a typical HTTP/TCP deployment.

Can route by path, host, header, or cookie. Examples: NGINX and HAProxy mode http.

Maintains transport state and request-level processing.

Enables HTTP routing and pooling; consumes CPU/memory for protocol processing.

Note: “one TCP connection” refers to a TCP client/server connection through a forwarding LB, not a direct physical link. HTTP/3 uses QUIC/UDP, so TCP counts do not apply to that mode.

2. Inside an L4 NAT load balancer

It acts like a NAT router with backend-selection logic. Backend membership and per-flow NAT state serve different purposes.

ComponentPurposeImplementation / updates
Backend registryLists eligible backends, such as 10.0.0.11:8080 and 10.0.0.12:8080.Static configuration, Keepalived health checks, Consul/etcd, or Kubernetes EndpointSlices. Local snapshot in the LB.
Connection (flow) tableMaps each client flow to a chosen backend and its NAT translation.Usually memory-resident, with hash-based lookup. Entries are created for flows and expire on timeout/closure.
5-tuple flow identity(source IP, source port, destination IP, destination port, protocol).Used to identify flow direction and find the corresponding mapping.
NAT packet pathDNAT on requests; reverse translation on responses.LB must receive both directions and preserve connection-to-backend affinity.
Control plane vs data planeControl plane updates eligible backend membership; data plane forwards packets.Service discovery is not queried on every packet.

Backend discovery pipeline

Consul / etcd / Config→LB Controller→IPVS Backend Table

No PostgreSQL is required. A separate service registry becomes useful when backend instances join and leave dynamically.

Flow mapping example

Client request to LB VIP
192.0.2.10:50000 → 203.0.113.10:443
                 DNAT ↓

The server replies through the LB; reverse NAT makes the reply appear to originate from the VIP.

Example memory estimate: at an assumed 512 bytes of state/overhead per flow, 1 million concurrent flows would use about 512 MB. This is an illustration, not an IPVS benchmark.

Takeaway: L4 NAT = packet forwarding + NAT + backend selection + flow tracking. L4 DSR bypasses the LB on replies. L4 full proxies terminate TCP; L7 proxies additionally understand application protocols such as HTTP.
